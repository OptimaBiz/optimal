# CONTENT_AND_SEO_RULES.md

## Назначение документа

Этот документ задаёт **обязательные правила по контенту, page identity, SEO-метаданным и смысловой уникальности страниц** сайта «Оптимальный вариант».

Документ нужен для того, чтобы:
- не появлялись клоновые страницы;
- не дублировались `H1`, `title`, `description` и `canonical`;
- каждая услуга имела свою чёткую идентичность;
- пользователь и поисковик получали **одинаковый и недвусмысленный сигнал** о назначении страницы;
- сайт оставался экспертным, строгим и понятным;
- особенно корректно были оформлены страницы по **аккредитации в ФСА**.

---

## Главный принцип

У каждой страницы должна быть **своя собственная page identity**.

Это означает, что страница должна быть различима по:
- URL;
- `title`;
- `meta description`;
- `canonical`;
- `H1`;
- hero lead / первому объясняющему абзацу;
- breadcrumb label;
- CTA первого экрана;
- скрытым полям формы / page scenario / service labels, если они используются;
- внутренней смысловой структуре.

### Недопустимо
Создавать новую страницу методом:
- копирования соседней страницы;
- частичной замены заголовка;
- сохранения чужих `canonical`;
- сохранения чужих hidden field / сценариев;
- сохранения соседнего `H1`;
- сохранения почти идентичного lead-текста.

Если страница про другую услугу — **все ключевые идентификаторы страницы должны быть другими**.

## Обязательные page-level элементы для service pages

Для каждой service page обязательно проверить и поддерживать в актуальном состоянии:

1. `<title>`
2. `<meta name="description">`
3. `<link rel="canonical">`
4. `<meta property="og:title">`
5. `<meta property="og:description">`
6. `<meta property="og:url">` — если используется
7. `<meta name="twitter:title">`
8. `<meta name="twitter:description">`
9. `<h1>`
10. hero lead / подзаголовок / первый explanatory text
11. breadcrumb label
12. page-specific CTA
13. hidden service / `service_scenario` / `data-service` / `data-page`, если используются
14. якорные ссылки и внутренние ссылки на страницу
15. название страницы в меню / мегаменю / related links, если оно там выведено явно

Если изменилась суть страницы — нужно проверить **весь этот список**, а не только `H1`.

---

## Правила для `title`

### Общие требования
`<title>` должен:
- однозначно описывать страницу;
- отражать реальную услугу;
- отличаться от соседних страниц;
- не быть слишком общим;
- не быть копией title другой страницы.

### `title` должен
- содержать основную услугу;
- по возможности уточнять объект или тип процедуры;
- поддерживать экспертный характер страницы;
- быть понятным без чтения самой страницы.

### Недопустимо
- одинаковый `title` у разных услуг;
- “универсальные” тайтлы, которые можно переставить между страницами без потери смысла;
- title одной процедуры на странице другой процедуры.

### Правильная логика
Пользователь и поисковик должны понимать разницу между:
- аккредитацией;
- подтверждением компетентности;
- расширением области;
- замечаниями / выездной оценкой;
- ОИК;
- ОС.

---

## Правила для `meta description`

### Назначение
`meta description` не должен быть набором общих фраз.

Он должен:
- кратко объяснять суть услуги;
- указывать на тип задачи;
- усиливать различимость страницы;
- не быть клоном соседних descriptions.

### Хороший description
Описывает:
- что за услуга;
- для кого;
- в каком сценарии нужна;
- какой результат ожидается.

### Недопустимо
- переставлять один и тот же description между страницами;
- писать слишком общие descriptions в стиле “поможем оформить документы и пройти процедуру” на всех страницах подряд;
- использовать формулировки, не отличающие сложные ФСА-процедуры друг от друга.

---

## Правила для `canonical`

### Canonical всегда должен
- указывать на текущую страницу;
- соответствовать реальному URL;
- не вести на соседнюю услугу;
- не сохраняться по ошибке после копирования страницы.

### Недопустимо
- canonical страницы РОА на страницу подтверждения компетентности;
- canonical страницы замечаний на страницу общей аккредитации;
- canonical, который противоречит H1 и URL.

### Если есть сомнение
Проверять `canonical` вручную и по коду.  
Для страниц ФСА это обязательная часть любой проверки.

---

## Правила для `H1`

### H1 должен
- точно называть услугу;
- совпадать со смыслом страницы;
- отличать страницу от соседних услуг;
- быть понятным без дополнительного контекста.

### H1 не должен
- быть просто “красивой фразой” без точности;
- дублировать H1 другой страницы;
- быть шире или уже, чем реальное содержание страницы;
- вводить в заблуждение относительно типа процедуры.

### Для ФСА особенно важно
Разводить по смыслу:

- **первичная аккредитация**
- **подтверждение компетентности**
- **расширение области аккредитации**
- **замечания ФСА и выездная оценка**
- **аккредитация ОИК**
- **аккредитация ОС**

Если H1 можно безболезненно переставить на соседнюю страницу — H1 плохой.

---

## Правила для OG / Twitter metadata

Если в проекте используются `og:*` и `twitter:*`, они должны:
- повторять корректную page identity;
- соответствовать текущей странице;
- не копироваться автоматически без проверки;
- не вступать в конфликт с `title`, `description`, `H1`.

### Обязательно проверить
- `og:title`
- `og:description`
- `og:url`, если есть
- `twitter:title`
- `twitter:description`

### Недопустимо
Когда в коде страницы замечаний OG-данные описывают ПК, РОА или общую аккредитацию.

---

## Правила для hero и первого explanatory блока

Первый экран должен сразу отвечать на вопрос:

**«О чём эта страница и в каком сценарии мне сюда?»**

### Hero должен
- подтверждать смысл H1;
- быстро объяснять услугу;
- не быть слишком абстрактным;
- не вести смыслом в соседнюю услугу.

### Hero lead / subtitle должен
- быть page-specific;
- отражать реальную процедуру;
- усиливать различимость страницы;
- помогать пользователю понять, подходит ли ему эта страница.

### Недопустимо
Оставлять после копирования hero lead, который описывает другую услугу.

---

## Правила для breadcrumb labels

Breadcrumb должен:
- соответствовать реальной странице;
- не вводить в заблуждение;
- быть синхронизирован с H1 и title;
- быть короче и тише hero, но семантически точным.

### Недопустимо
- breadcrumb “Подтверждение компетентности” на странице РОА;
- breadcrumb “Аккредитация лаборатории” на странице замечаний/выездной оценки;
- расхождение HTML и JS-словаря breadcrumbs.

Если breadcrumbs собираются из JS, include или partials — проверять реальный источник.

---

## Правила для CTA

CTA — это часть page identity.

### CTA должен
- соответствовать стадии клиента;
- соответствовать именно этой услуге;
- не быть механически одинаковым на всех страницах.

### Особенно для ФСА
Должны различаться CTA для:
- первичной аккредитации;
- подтверждения компетентности;
- расширения области;
- замечаний / выездной оценки.

### Недопустимо
Когда на странице замечаний CTA звучит как общий вход в аккредитацию, а на странице РОА — как CTA на ПК.

### Принцип
У каждой сложной страницы должен быть **свой основной следующий шаг**, а не абстрактное “Оставить заявку” без смыслового уточнения.

---

## Правила для скрытых полей формы и page scenarios

Если на сайте используются:
- hidden inputs;
- `service`;
- `service_scenario`;
- `data-service`;
- `data-page`;
- page labels;
- служебные значения, уходящие в форму, аналитику или CRM,

они обязаны соответствовать текущей странице.

### Недопустимо
- страница РОА отправляет значение “подтверждение компетентности”;
- страница замечаний отправляет “аккредитация лаборатории”;
- страница ОС или ОИК уходит в форме как другая услуга.

### Обязательное правило
После любого клонирования service page нужно проверять hidden/service fields отдельно.

---

## Правила различения похожих услуг

### Для ФСА различение обязательно

#### 1. Первичная аккредитация
Смысл:
- подготовка к первичному получению аккредитации;
- готовность системы;
- документы;
- персонал;
- оборудование;
- процедуры;
- область.

#### 2. Подтверждение компетентности
Смысл:
- очередная процедура подтверждения;
- контроль готовности;
- риски накопленных несоответствий;
- проверка актуального состояния;
- сопровождение перед ПК.

#### 3. Расширение области аккредитации
Смысл:
- новые методы;
- новые объекты;
- новые диапазоны;
- новые виды испытаний;
- готовность ресурсов под новую область.

#### 4. Замечания / выездная оценка
Смысл:
- уже есть замечания;
- требуется разбор и приоритизация;
- подготовка ответов;
- подготовка доказательств;
- сопровождение выездной оценки;
- антикризисный или срочный сценарий.

#### 5. ОИК
Смысл:
- аккредитация органа инспекционного контроля;
- область инспекции;
- независимость;
- процедуры;
- записи;
- компетентность персонала.

#### 6. ОС
Смысл:
- аккредитация органа по сертификации;
- процедуры сертификации;
- схема работы;
- беспристрастность;
- записи;
- компетентность;
- доказательная база.

### Требование
Эти шесть типов страниц не должны сливаться ни в метаданных, ни в hero, ни в CTA, ни в hidden fields.

---

## Правила различения услуг вне ФСА

Для всех других похожих страниц также обязательно различать:
- лицензирование vs обучение;
- общая страница направления vs точечная посадка;
- ISO 9001 vs ISO 14001 vs ISO 45001;
- общая НАКС-страница vs персонал НАКС vs технологии сварки НАКС;
- меддеятельность как направление vs лицензия на меддеятельность как конкретная услуга.

---

## Правила для внутренних ссылок

Внутренние ссылки должны:
- вести на правильную страницу;
- быть подписаны корректно;
- не вести пользователя в соседнюю услугу из-за старой подписи;
- поддерживать структуру сайта.

### Недопустимо
- ссылка “Расширение области аккредитации” ведёт на страницу ПК;
- связанный блок или карточка подписаны неверно;
- related links между ФСА-страницами создают путаницу.

---

## Правила для шаблонов и клонирования страниц

Если создаётся новая service page на основе существующей:

### Обязательно заменить и проверить
- URL / filename
- `<title>`
- `meta description`
- `canonical`
- `og:*`
- `twitter:*`
- `H1`
- hero lead
- breadcrumb label
- CTA первого экрана
- hidden inputs / service labels
- related links
- heading structure внутри страницы
- FAQ, если он page-specific

### Недопустимо
Оставлять старую семантику и рассчитывать “доделать потом”.

---

## Правила для FAQ

FAQ должен:
- закрывать дорогие и реальные возражения;
- соответствовать именно этой услуге;
- не быть общим набором вопросов, который одинаково лежит на всех страницах.

### Для сложных услуг FAQ должен отвечать на:
- сроки;
- стоимость;
- документы;
- степень готовности;
- замечания;
- риски;
- что делает клиент;
- что делает компания;
- что происходит, если ситуация срочная.

---

## Правила по стилю текста

### Тональность
Текст сайта должен быть:
- уверенным;
- спокойным;
- экспертным;
- точным;
- деловым;
- без рекламной истерики;
- без “кричащих” обещаний;
- без инфостиля ради инфостиля.

### Недопустимо
- пустые рекламные фразы;
- “продающие” клише без смысла;
- чрезмерная агрессия;
- обещания без опоры на процедуру;
- гиперболы в духе “сделаем всё быстро и без проблем” там, где услуга объективно сложная.

### Предпочтительно
Писать через:
- сценарий клиента;
- конкретику;
- управляемость процесса;
- документы;
- этапы;
- проверку готовности;
- контрольные точки;
- результат.

---

## Правила для headings внутри страницы

### H2 и H3 должны
- отвечать на реальные вопросы пользователя;
- поддерживать маршрут принятия решения;
- быть семантически точными;
- не быть просто SEO-рубриками.

### Плохо
- “Преимущества компании”
- “Почему выбирают нас”
- “Наши сильные стороны”

### Лучше
- “Что проверяем перед подачей”
- “Какие документы и доказательства нужны”
- “Что входит в сопровождение”
- “Где чаще всего возникают замечания”
- “Как проходит работа по этапам”

---

## Правила для legal-страниц

Юридические страницы:
- не требуют продающей SEO-семантики;
- должны быть максимально чистыми;
- должны иметь читаемый title;
- должны иметь корректный canonical;
- не должны конкурировать с коммерческими service pages.

---

## Правила для noindex / служебных страниц

Если есть служебные или персональные страницы:
- их role должна быть ясной;
- если они не являются частью основного коммерческого маршрута, это должно быть осознанно;
- они не должны конфликтовать по тону и смыслу с основным брендом, если доступны пользователям.

## Что делать, если найдена клоновая ошибка

Если обнаружено, что страница:

* наследует чужой H1;
* наследует чужой canonical;
* наследует чужой CTA;
* наследует чужое hidden field;
* наследует чужой lead;

то это считается **критической ошибкой доверия и page identity**.

### Порядок исправления

1. исправить identity-контур страницы;
2. проверить все page-level элементы;
3. проверить внутренние ссылки;
4. только потом переходить к дизайну и визуальной пересборке.

## Приоритет при конфликте

Если возникает конфликт между:

* этим документом;
* `AGENTS.md`;
* конкретным ТЗ,

приоритет такой:

1. прямое ТЗ пользователя;
2. `AGENTS.md`;
3. этот `CONTENT_AND_SEO_RULES.md`;
4. локальные документы подпапок, если они есть и применимы.

Если конфликт найден — его нельзя игнорировать молча.

## Финальный стандарт качества

Хорошо оформленная страница сайта — это страница, у которой:

* точный URL;
* точный и уникальный H1;
* корректный title;
* корректный description;
* корректный canonical;
* согласованные OG/Twitter;
* hero, который не врёт;
* breadcrumb, который не путает;
* CTA, который соответствует стадии клиента;
* форма, которая отправляет правильный сценарий;
* контент, который нельзя безболезненно переставить на соседнюю услугу.

Если страницу можно перепутать с другой услугой — страница оформлена плохо.

```
```
