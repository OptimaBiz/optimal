# UI_SYSTEM_RULES.md

## Назначение документа

Этот документ задаёт **обязательные UI/UX-правила и visual-direction рамку** для сайта «Оптимальный вариант».

Он нужен для того, чтобы:
- сайт сохранял единый характер;
- новые страницы и правки не ломали общий уровень качества;
- Codex и другие исполнители не превращали сайт в набор случайных решений;
- интерфейс оставался строгим, дорогим, минималистичным и экспертным;
- особенно сильным и зрелым выглядел раздел **«Аккредитация в ФСА»**.

---

## Главный визуальный принцип

Сайт должен ощущаться как:

- строгий;
- чистый;
- спокойный;
- дорогой;
- уверенный;
- экспертный;
- не шумный;
- не шаблонный;
- не «рекламно-крикливый»;
- не «техническая демка».

### Правильная ассоциация
Не «красивый лендинг», а **сильный B2B-партнёр по сложным регуляторным процедурам**.

---

## Главный UX-принцип

Каждая страница должна быстро отвечать на 4 вопроса:

1. **Что это за услуга?**
2. **Подходит ли она под мою ситуацию?**
3. **Что именно здесь делают?**
4. **Какой следующий шаг мне сделать?**

Если интерфейс не помогает ответить на эти вопросы, он работает плохо, даже если выглядит аккуратно.

---

## Приоритеты по визуальному качеству

### Приоритет №1
ФСА-страницы:
- `akkreditaciya.html`
- `akkreditaciya-ispytatelnaya-laboratoriya.html`
- `akkreditaciya-podtverzhdenie-kompetentnosti-laboratorii.html`
- `akkreditaciya-rasshirenie-oblasti-laboratorii.html`
- `akkreditaciya-zamechaniya-vyezdnaya-ocenka.html`
- `akkreditaciya-organ-inspekcionnogo-kontrolya.html`
- `akkreditaciya-organ-po-sertifikacii.html`

Именно эти страницы должны быть **эталоном зрелого и дорогого B2B-UI**.

### Приоритет №2
Главная, каталог услуг, лицензирование, аттестация, ISO, НАКС.

### Приоритет №3
Legal и служебные страницы.

---

## Что считается хорошим UI для этого проекта

Хороший UI здесь — это не украшение.

Это UI, который:
- задаёт правильную иерархию;
- помогает сканированию;
- не утомляет на длинных страницах;
- не делает всё одинаково важным;
- поддерживает доверие;
- подчёркивает экспертность;
- убирает ощущение шаблонности;
- помогает конверсии без давления.

---

## Что недопустимо

### Визуально недопустимо
- бесконечные одинаковые карточки подряд;
- одинаковые по весу секции без ритма;
- декоративные иконки ради декора;
- агрессивные градиенты;
- избыточные тени;
- дешёвые hover-эффекты;
- слишком «модный» визуал, не соответствующий B2B-нише;
- случайные акценты, не поддерживающие структуру.

### UX-недопустимо
- два равносильных CTA без иерархии;
- hero, не объясняющий страницу;
- breadcrumbs, которые путают;
- page layout, где нельзя быстро понять маршрут;
- формы, не связанные со сценарием страницы;
- когда все блоки выглядят одинаково важными;
- когда длинная страница визуально монотонна.

---

## Visual direction

### Базовый характер
- светлая база;
- аккуратные нейтральные поверхности;
- сдержанный тёмно-синий / глубокий холодный акцент;
- минимум визуального шума;
- акцент на структуру, а не на декоративность.

### Что должно создавать premium-feel
- точная типографика;
- чистые отступы;
- ясная иерархия;
- сдержанные бордеры;
- умеренная глубина;
- редкие, но сильные акцентные панели;
- визуально зрелые CTA;
- продуманная композиция длинных страниц.

### Что НЕ создаёт premium-feel
- много карточек одного вида;
- много одинаковых CTA;
- псевдо-дорогие эффекты;
- крупные размазанные тени;
- кислотные акценты;
- “креативность ради креативности”.

---

## Правила по page architecture

Для каждой коммерческой service page должен читаться понятный каркас.

### Базовый skeleton service page
1. Breadcrumbs
2. Hero
3. Сценарии обращения / для кого страница
4. Что входит / состав работ / область помощи
5. Процесс / этапы
6. Результат / что получает клиент
7. FAQ
8. Финальный CTA
9. Контактный блок / форма

### Что может усиливаться по смыслу
Для сложных страниц ФСА дополнительно допустимы и желательны:
- блоки рисков;
- таблицы документов;
- контрольные точки;
- roadmap;
- матрица замечаний;
- экспертные панели;
- блок “что определим на первом разборе”;
- блок “что зависит от текущей готовности”.

### Что нельзя
- превращать каждую страницу в абсолютно одинаковый шаблон;
- убирать различие в сложности между ФСА, обучением, ISO и legal-страницами;
- делать длинную страницу только как цепочку одинаковых grid-секций.

---

## Hero rules

### Hero обязан
- быстро объяснять услугу;
- содержать точный H1;
- иметь короткий expert lead;
- иметь 1 primary CTA;
- максимум 1 secondary CTA;
- не перегружаться лишним текстом;
- не врать относительно содержания страницы.

### Hero не должен
- быть декоративным баннером без смысла;
- быть слишком пустым;
- быть слишком длинным;
- дублировать общие продающие фразы;
- обещать одну процедуру на странице другой процедуры.

### Для ФСА-страниц
Hero должен ощущаться сильнее, чем на обычных страницах:
- допускается summary-panel;
- допускается короткий список контрольных точек;
- допускается блок “что разберём на первом обращении”;
- допускаются status / scenario badges, если они спокойные и реально помогают.

---

## Правила по секциям

### Каждая секция должна иметь роль
Секция не должна существовать “потому что так принято на лендингах”.

Каждая секция должна отвечать на конкретную задачу:
- объяснить услугу;
- помочь выбрать сценарий;
- показать риски;
- показать состав работ;
- показать этапы;
- усилить доверие;
- закрыть возражения;
- довести до действия.

### Не допускается
- несколько подряд секций, которые по сути делают одно и то же;
- одинаковая подача “сценарии / преимущества / что входит / почему мы” через один и тот же паттерн;
- секции, которые можно переставить местами без потери смысла.

---

## Правила по карточкам

### Главный принцип
`service-card` не должен быть универсальным контейнером для всего.

Сайт не должен строиться полностью на одинаковых карточках.

### Допустимые типы карточек
В проекте должны различаться как минимум такие роли:

- `service-card` — услуга / направление
- `scenario-card` — сценарий обращения
- `risk-card` — замечание / риск / зона внимания
- `deliverable-card` — результат / артефакт / выход этапа
- `expert-note` — пояснение / важная экспертная заметка
- `checklist-card` — компактная проверка / критерии готовности

### Правила использования
- не более одной большой однотипной карточной сетки подряд;
- после карточной сетки желательно менять паттерн секции;
- карточки не должны делать все смыслы одинаково важными;
- карточка должна быть сканируемой и короткой;
- если контент требует процесса или матрицы, не надо насильно запихивать его в карточки.

### Недопустимо
- три-четыре секции подряд с одинаковым `grid + card`;
- карточками показывать timeline;
- карточками показывать всё подряд: услуги, преимущества, документы, риски, этапы, FAQ.

---

## Правила по CTA

### Общий принцип
CTA должен соответствовать **стадии пользователя**, а не просто занимать место на странице.

### Иерархия CTA
- **Primary CTA** — главный следующий шаг
- **Secondary CTA** — уточняющее или альтернативное действие
- **Tertiary / text CTA** — вспомогательная ссылка

### Что должен делать CTA
- быть понятным;
- быть привязанным к сценарию;
- не быть одинаковым на всех страницах без причины;
- не конкурировать сам с собой.

### Для ФСА желательно различать
- первичная аккредитация;
- ПК;
- РОА;
- замечания / выездная оценка.

### Плохо
- “Получить консультацию” везде и всегда;
- secondary CTA, ведущий в ту же точку, что primary;
- два primary CTA одинакового веса в одном блоке.

### Хорошо
- primary = следующий рабочий шаг;
- secondary = уточнить сценарий / перейти к смежной задаче / посмотреть related direction.

---

## Правила по кнопкам

### Система кнопок должна быть единой
Нельзя, чтобы на разных страницах:
- разный визуальный вес primary;
- случайные размеры;
- разная логика hover;
- разные отступы;
- разные радиусы без системы.

### Primary button
Primary:
- главный цветовой акцент;
- только для основного действия;
- самый заметный action в блоке;
- не должен использоваться 5 раз подряд без смысла.

### Secondary button
Secondary:
- визуально слабее primary;
- не дубль primary;
- не должна спорить с главным действием;
- должна быть аккуратной и читаемой.

### Large button
Используется только:
- в hero;
- в финальном CTA;
- иногда в ключевых сценарных блоках.

### Недопустимо
- большая кнопка в каждом втором блоке;
- кнопка ради эффекта;
- анимация ради анимации;
- слишком “мягкий”, “пузырьковый” или “игрушечный” вид.

---

## States rules

### Hover
Hover должен:
- быть заметным;
- быть спокойным;
- усиливать чувство контроля;
- не прыгать слишком сильно.

### Focus-visible
Обязателен для:
- кнопок;
- ссылок;
- полей формы;
- элементов меню;
- интерактивных карточек.

Focus-visible должен:
- быть читаемым;
- быть аккуратным;
- не быть грубым;
- не пропадать.

### Active
Active должен создавать ощущение реального нажатия, а не быть копией hover.

### Disabled
Disabled должен быть:
- очевидным;
- контрастно понятным;
- не путаться с normal state.

### Недопустимо
- отсутствие focus-visible;
- hover с сильным “lift” и дешёвым эффектом;
- states, отличающиеся между страницами случайно.

---

## Правила по типографике

### Общий принцип
Типографика должна быть:
- спокойной;
- читаемой;
- структурной;
- деловой;
- не “редакционно-крикливой”;
- не рыхлой.

### H1
- точный;
- page-specific;
- без лишней длины;
- должен читаться быстро;
- должен быть визуально доминирующим, но не агрессивным.

### H2
- должны звучать как ответы на реальные вопросы;
- не должны быть пустыми SEO-ярлыками;
- должны хорошо сканироваться на длинной странице.

### H3
- подчинённые, но чёткие;
- не слишком мелкие;
- не слишком декоративные.

### Paragraphs
- хорошая ширина строки;
- нормальный line-height;
- не делать слишком длинные полотна;
- разбивать длинный текст на смысловые фрагменты.

### Недопустимо
- слишком длинные строки;
- визуальная рыхлость;
- слишком мелкие подзаголовки;
- H2 и H3 без различимого веса.

---

## Правила по вертикальному ритму и spacing

### Вертикальный ритм должен
- давать воздух;
- подчеркивать смену смыслов;
- не превращать страницу в бесконечную одинаковую ленту;
- поддерживать премиальное восприятие.

### Что важно
- одинаковые типы секций — одинаковый базовый ритм;
- разные типы секций — разный визуальный вес;
- крупные смысловые переходы должны ощущаться;
- плотные списки должны чередоваться с более свободными блоками.

### Где обычно нужен воздух
- после больших карточных сеток;
- перед важными CTA;
- между смысловыми этапами;
- в hero длинных страниц;
- вокруг editorial-блоков.

### Недопустимо
- слишком плотная верстка;
- слишком пустая верстка;
- одинаковые отступы везде, независимо от роли секции.

---

## Правила по layout variety

### Главный принцип
Длинные страницы не должны быть монотонными.

Нужно чередовать паттерны секций:

- grid
- split layout
- roadmap
- checklist
- table
- risk matrix
- expert-note
- CTA strip
- summary block

### Особенно важно для ФСА
ФСА-страницы не должны выглядеть как набор из 10 почти одинаковых секций.

### Недопустимо
`section-head + services-grid + service-card` как основной паттерн всей длинной страницы.

---

## Правила по этапам работ

### Этапы должны показывать
- действие;
- результат;
- артефакт;
- контрольную точку;
- при необходимости — распределение ответственности.

### Хороший этап
Не просто “анализируем документы”, а:
- что анализируем;
- что выявляем;
- что выдаём;
- что это меняет дальше.

### Плохо
Этапы как обычный список карточек без ощущения маршрута.

### Правильный паттерн
Для серьёзных услуг:
- roadmap;
- numbered sequence;
- step + deliverable + checkpoint.

---

## Правила по блокам рисков

### Когда использовать
На сложных услугах, особенно:
- ФСА;
- лицензирование;
- НАКС;
- процедуры с замечаниями и проверками.

### Как подавать
Не как “преимущества”, а как:
- зоны риска;
- типовые замечания;
- последствия;
- как закрываем;
- что проверяем.

### Предпочтительный формат
- risk matrix;
- numbered risk list;
- structured expert notes.

### Недопустимо
Прятать важные риски в общих карточках “почему выбирают нас”.

---

## Правила по таблицам и матрицам

### Таблицы и матрицы — допустимы и желательны
Для этого проекта таблица часто выглядит **дороже и профессиональнее**, чем ещё одна карточная сетка.

### Когда таблица лучше карточек
- документы;
- требования;
- сценарии;
- этапы и результаты;
- сравнение вариантов;
- состав работ;
- различие между услугами.

### Требования
- чистая структура;
- хороший mobile fallback;
- не делать перегруз колонками;
- использовать только если таблица реально повышает ясность.

---

## Правила по expert-note / editorial blocks

### Зачем нужны
Чтобы сайт не был только “сеткой блоков”, а имел экспертную глубину.

### Где использовать
- в ФСА;
- на страницах со сложным выбором;
- после плотной секции;
- перед CTA;
- в местах, где нужен важный комментарий специалиста.

### Что это может быть
- “Что важно понять до подачи”
- “Частая ошибка”
- “Что определим на первом разборе”
- “Что влияет на сроки и стоимость”
- “Что остаётся на стороне клиента”

### Недопустимо
Превращать expert-note в декоративную цитату без пользы.

---

## Правила по FAQ

### FAQ нужен не ради SEO, а ради снятия дорогих возражений
Он должен закрывать:
- сроки;
- стоимость;
- готовность;
- документы;
- риски;
- замечания;
- роль клиента;
- формат работы;
- срочные сценарии.

### FAQ не должен
- быть набором общих вопросов;
- повторять текст выше без добавленной пользы;
- быть одинаковым для соседних сложных услуг.

---

## Правила по breadcrumbs

### Breadcrumbs должны
- быть тихими;
- быть точными;
- не конкурировать с hero;
- поддерживать структуру сайта;
- совпадать по смыслу со страницей.

### Breadcrumbs нельзя
- делать слишком заметными;
- использовать как декоративный элемент;
- оставлять несинхронизированными с H1/URL/page identity.

---

## Правила по меню и мегаменю

### Меню должно
- быстро объяснять структуру сайта;
- не делать все направления одинаково важными;
- выделять ФСА как флагманское направление;
- быть понятным и на desktop, и на mobile.

### Мегаменю должно
- быть полезным;
- не быть перегруженным;
- группировать связанные услуги;
- не выглядеть как неструктурированный список ссылок.

### Недопустимо
- хаотичный порядок групп;
- одинаковый визуальный вес у критичных и второстепенных ссылок;
- mobile menu как деградировавшая версия desktop без логики.

---

## Правила по формам

### Контактный блок и форма — сильная часть сайта
Их нельзя радикально ломать без прямого запроса.

### Что важно
- ясность;
- спокойствие;
- доверие;
- читаемость;
- корректные states;
- логичное соотношение текста и полей.

### Допустимо
- точечная унификация отступов;
- улучшение состояний;
- корректировка скрытых page-specific полей;
- мягкая привязка к конкретной услуге.

### Недопустимо
- превращать форму в “тяжёлую CRM-анкету”;
- перегружать контактный блок;
- делать резкий визуальный разрыв с остальным сайтом.

---

## Правила по иконкам

### Иконки допустимы только если помогают сканированию
Они должны:
- усиливать структуру;
- быть нейтральными;
- не спорить с типографикой;
- не превращать сайт в “иконный каталог”.

### Недопустимо
- иконки ради заполнения пространства;
- слишком яркие или “мультяшные” иконки;
- разные визуальные стили иконок на одной странице.

---

## Правила по изображениям и декоративным элементам

### Общий принцип
Изображения и декоративные элементы вторичны по отношению к структуре.

### Изображения должны
- поддерживать доверие;
- быть чистыми;
- быть уместными;
- не разрывать строгий характер сайта.

### Недопустимо
- декоративный шум;
- случайные иллюстрации;
- “стоковый” визуал, который удешевляет услугу;
- фоновые эффекты ради эффекта.

---

## Правила по mobile UX

### Мобильная версия не должна быть “сжатым desktop”
На mobile нужно отдельно проверять:
- hero;
- CTA;
- карточные сетки;
- roadmap;
- таблицы;
- breadcrumbs;
- меню;
- форму;
- scroll-top;
- общий ритм.

### На mobile особенно важно
- удобный скролл;
- читаемые карточки;
- не перегруженные hero;
- корректные кнопки;
- отсутствие конфликтов отступов;
- понятный маршрут пользователя.

### Недопустимо
- слипшиеся CTA;
- слишком узкие карточки;
- сложные desktop-паттерны без адаптации;
- декоративные решения, которые на mobile выглядят дешево.

---

## Правила по desktop UX

### Desktop должен давать ощущение управляемости
Особенно на длинных страницах пользователь должен чувствовать:
- ясную иерархию;
- смысловой маршрут;
- контроль;
- отсутствие визуальной усталости.

### Хороший desktop layout
- достаточно воздуха;
- хороший max-width;
- сильный hero;
- понятные переходы между секциями;
- зрелая композиция.

---

## Правила различия страниц по сложности

### Все страницы не должны выглядеть одинаково тяжёлыми
- ФСА — самый зрелый, глубокий и экспертный visual layer
- лицензирование — строгое и доказательное
- НАКС / аттестация — структурное и техническое
- ISO / обучение — легче и каталоговее
- legal — максимально тихое и функциональное

### Недопустимо
Когда legal-page визуально похожа на сложную экспертную посадочную, а ФСА — на общий SEO-лендинг.

---

## Контрольный список для UI-задач

Перед сдачей задачи нужно проверить:

### По странице
- hero корректен;
- H1 читается;
- CTA логичен;
- секции не дублируют друг друга;
- ритм страницы не монотонный;
- есть правильная иерархия;
- breadcrumb корректен.

### По компонентам
- кнопки единообразны;
- карточки не используются хаотично;
- states аккуратны;
- spacing чистый;
- typography не просела;
- mobile не сломан.

### По длинным страницам
- нет 3+ одинаковых секций подряд без смены паттерна;
- этапы не выглядят как обычные карточки;
- риски/документы/результаты поданы структурно, а не общими преимуществами.

Если видишь конфликт — не игнорируй молча.

## Финальный стандарт качества

Хорошее UI-решение для этого проекта — это решение, которое:

* делает сайт строже и дороже сайт строже и дороже;
* делает маршрут яснее;
* не создаёт шум;
* не ломает хороший базовый стиль;
* усиливает доверие;
* уменьшает шаблонность;
* делает ФСА визуально и UX-сильнее;
* остаётся минималистичным, но не скучным.

Если после правки страница стала просто “эффектнее”, но не стала яснее, строже и взрослее — правка плохая.
