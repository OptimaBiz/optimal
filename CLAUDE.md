# CLAUDE.md

## Назначение файла

Этот файл задаёт правила работы Claude/ИИ-агентов с проектом сайта «Оптимальный вариант».

Сайт — коммерческий B2B-сайт консультационной компании по разрешительным, аккредитационным, сертификационным и юридико-регуляторным услугам для бизнеса.

Главная цель любых изменений: повышать доверие, понятность оффера, SEO-качество, рекламную конверсию и техническую стабильность сайта, не ломая существующие страницы, формы, навигацию и аналитику.

---

## Язык и тон

- Все пользовательские тексты, заголовки, CTA, метаописания и интерфейсные формулировки писать на русском языке.
- Английские термины использовать только там, где они являются техническими или общеупотребимыми: `SEO`, `CTA`, `UI`, `UX`, `schema.org`, `Open Graph`.
- Тон сайта: деловой, уверенный, экспертный, без канцелярского перегруза и без дешёвого инфобизнеса.
- Не использовать агрессивные обещания, страховые манипуляции и юридически рискованные гарантии.

Разрешено:

- `поможем подготовиться`
- `оценим риски`
- `проверим документы`
- `подготовим план исправлений`
- `снизим вероятность замечаний`
- `сопроводим процедуру`

Запрещено:

- `гарантируем прохождение`
- `100% одобрение`
- `точно получите аккредитацию`
- `обязательная переаккредитация всех`
- `иначе лишат аккредитации`
- любые обещания результата, который зависит от госоргана, экспертов или регулятора.

## Общий workflow

Перед изменениями:

1. Проверить текущую ветку и состояние репозитория.
2. Для новой задачи стартовать от актуального `main`, если это возможно в текущем окружении.
3. Создать отдельную ветку под задачу.
4. Не пушить напрямую в `main`.
5. Не смешивать несколько крупных задач в один PR.

После изменений:

1. Кратко описать, что изменено.
2. Перечислить изменённые файлы.
3. Указать, какие проверки выполнены.
4. Указать ограничения, если что-то не удалось проверить.

Формат финального отчёта:

```text
Summary
- ...

Changed files
- ...

Checks
- ...

Notes / limitations
- ...
```

## Технические инварианты

- Не ломать существующие URL.
- Не удалять существующие страницы без отдельного явного задания.
- Не менять структуру форм, если не понятно, как они отправляются и обрабатываются.
- Не ломать текущие поля формы, hidden fields, сценарии, consent-блоки и редиректы после отправки.
- Не отключать аналитику, цели, обработчики кликов и события формы.
- Не удалять метатеги, Open Graph, favicon, sitemap, robots, canonical без причины.
- Не добавлять внешние зависимости без явной необходимости.
- Не переписывать весь сайт ради одной страницы.
- Не создавать неиспользуемые CSS/JS-блоки.
- Не оставлять битые ссылки, пустые href, `#` без обработчика или временные заглушки.

## Структура и переиспользование

Перед созданием новой страницы нужно посмотреть, как устроены существующие страницы:

- header;
- footer;
- навигация;
- блок услуг;
- хлебные крошки, если есть;
- форма заявки;
- CSS-классы страниц услуг;
- подключение JS;
- sitemap;
- smoke/e2e tests.

Новые страницы должны максимально переиспользовать существующие паттерны сайта.

Если есть готовые блоки для service page / landing page — использовать их, а не создавать полностью новый визуальный стиль.

## SEO-правила

Для каждой новой коммерческой страницы обязательно:

- уникальный `<title>`;
- уникальный `meta description`;
- один понятный `h1`;
- логичная иерархия `h2`/`h3`;
- человекопонятный URL;
- canonical, если в проекте уже используется canonical;
- Open Graph, если используется на других страницах;
- добавление в sitemap, если sitemap статический;
- внутренняя перелинковка с релевантных страниц;
- отсутствие keyword stuffing.

SEO-текст должен помогать продаже, а не выглядеть как набор ключей.

---

## Хлебные крошки

Для новых страниц услуг и посадочных страниц хлебные крошки обязательны.

Правила:

- крошки размещать над hero или в начале основного контента;
- структура должна быть семантичной и доступной;
- текущий пункт должен быть отмечен как текущая страница;
- ссылки должны вести только на реально существующие страницы;
- не создавать фейковые промежуточные страницы ради крошек.

Пример:

```text
Главная → Аккредитация в ФСА → Подтверждение компетентности ОС СМК
```

---

## Внутренняя перелинковка

Для новой страницы нужно добавить ссылки:

- с ближайшей родительской страницы;
- с релевантных страниц услуг;
- из блоков cross-sell / related services;
- при необходимости из карточек услуг на главной или странице услуг.

Анкоры должны быть естественными.

Хорошие анкоры:

- `Подтверждение компетентности ОС СМК`
- `Подготовка ОС СМК к ПК`
- `Проверка области аккредитации ОС СМК`
- `Актуализация области аккредитации ОС СМК`

Плохие анкоры:

- `сюда`
- `тут`
- `подробнее` без контекста, если рядом нет ясного заголовка.

---

## Cross-sell / related services

На страницах услуг должен быть блок связанных услуг, если он уместен.

Правила:

- ссылки только на существующие страницы;
- каждая карточка: название услуги, короткое описание, ссылка;
- блок должен помогать пользователю выбрать соседнюю услугу, а не выглядеть как баннер;
- не перегружать блок десятками ссылок;
- не создавать страницы-заглушки ради cross-sell.

---

## Формы и CTA

CTA должен вести к форме или понятному целевому действию.

Для новых посадочных страниц:

- primary CTA должен быть виден на первом экране;
- secondary CTA может вести к форме, консультации или блоку процесса;
- кнопки должны иметь понятный текст, а не абстрактное `Отправить` / `Подробнее` там, где нужен коммерческий контекст;
- если есть hidden fields для сценария услуги, заполнять их аккуратно и совместимо с существующим JS;
- если расширение формы может сломать обработку, не менять backend/структуру отправки без отдельного задания.

Хорошие CTA:

- `Проверить готовность`
- `Получить первичный разбор`
- `Обсудить процедуру`
- `Отправить заявку`

---

## Юридическая и регуляторная аккуратность

Проект работает с чувствительными темами: аккредитация, сертификация, лицензирование, Росаккредитация, разрешительная документация.

Правила:

- Не утверждать спорные юридические факты без проверки.
- Не писать, что услуга гарантирует решение госоргана.
- Не подменять официальные процедуры маркетинговыми обещаниями.
- Не использовать формулировки, которые могут выглядеть как обход требований.
- При упоминании приказов, постановлений, ГОСТов и методических рекомендаций проверять номер, дату и область применения.
- Если факт требует актуальности, отметить необходимость проверки источника.

---

## Специальный контекст: ОС СМК и подтверждение компетентности

Для страниц и задач по органам по сертификации систем менеджмента использовать аккуратное позиционирование:

- `ОС СМК`;
- `орган по сертификации систем менеджмента`;
- `подтверждение компетентности`;
- `Росаккредитация`;
- `область аккредитации`;
- `актуализация области аккредитации`;
- `методические рекомендации`;
- `ОКВЭД 2`;
- `ГОСТ Р ИСО/МЭК 17021-1-2017`.

Главный смысл такой страницы:

> Клиент должен сразу понять, что здесь помогают не с абстрактной сертификацией, а с подготовкой ОС СМК к ПК, проверкой области аккредитации, формулировок, стандартов, ОКВЭД и рисков замечаний.

Безопасные формулировки:

- `проверим область аккредитации`;
- `оценим риски замечаний`;
- `подготовим план доработки`;
- `поможем подготовиться к процедуре`;
- `разберём комплект документов`.

## UI/UX правила

- Первый экран должен отвечать на вопрос пользователя: куда он попал, какую задачу решают, почему можно оставить заявку.
- На мобильных устройствах CTA и форма должны быть легко доступны.
- Не делать длинные простыни текста без структуры.
- Использовать списки, карточки, чек-листы, этапы процесса.
- Не перегружать страницу декоративными элементами.
- Не создавать визуальный стиль, конфликтующий с остальным сайтом.
- Проверять, что шапка, мобильное меню, footer, форма и якоря работают после изменений.

---

## Производительность и доступность

- Не добавлять тяжёлые изображения без оптимизации.
- Не добавлять внешние скрипты без необходимости.
- Сохранять корректные `alt` для значимых изображений.
- Кнопки и ссылки должны быть фокусируемыми и иметь понятный текст.
- Не использовать кликабельные `div`, если можно использовать `button` или `a`.
- Модальные окна и consent-блоки не ломать.

---

## Тестирование

После изменений проверить минимум:

- новая страница открывается;
- существующие ключевые страницы открываются;
- desktop layout не развален;
- mobile layout не развален;
- header/menu работает;
- CTA-якоря работают;
- форма отображается и не ломается JS;
- внутренние ссылки не битые;
- sitemap обновлён, если он статический;
- smoke tests обновлены, если список ключевых страниц изменился.

Если в проекте есть команды проверки, использовать их.

Типовые проверки, если применимы:

```bash
npm run build
npm run lint
npm run typecheck
npm test
npx playwright test
```

Если команды отсутствуют или окружение не позволяет их выполнить, честно указать это в финальном отчёте.

---

## Правила для рекламных посадочных страниц

Страница под рекламу должна иметь:

- точное совпадение с рекламным обещанием;
- ясный hero;
- CTA на первом экране;
- блок `Для кого`;
- блок `Что проверяем / что делаем`;
- блок `Что получает клиент`;
- процесс работы;
- форму заявки;
- доверительные элементы;
- связанные услуги;
- внутреннюю перелинковку;
- SEO-метаданные.

Страница не должна быть общей витриной всех услуг.

---

## Stop conditions

Остановиться и явно сообщить, если:

- неясно, какая страница является родительской;
- отсутствует форма и непонятно, как её безопасно создать;
- изменение формы требует backend-правок;
- найден конфликт URL;
- sitemap генерируется автоматически и не нужно править статический файл;
- существующие тесты падают по причинам, не связанным с задачей;
- рабочая ветка содержит чужие незакоммиченные изменения.

---

## Запрещённые действия без отдельного задания

- Полный редизайн сайта.
- Массовая перепись всех страниц.
- Удаление старых URL.
- Изменение домена, аналитики, целей, форм и обработчиков заявок.
- Замена всей CSS-архитектуры.
- Добавление CMS.
- Добавление новых зависимостей.
- Изменение политики конфиденциальности или юридических документов без явного задания.

---

## Критерий качества

Изменение считается хорошим, если:

- пользователь понимает оффер за 5 секунд;
- страница выглядит частью текущего сайта;
- CTA ведёт к понятному действию;
- форма не сломана;
- SEO-основа заполнена;
- есть хлебные крошки;
- есть внутренняя перелинковка;
- есть cross-sell по реальным услугам;
- нет юридически рискованных обещаний;
- существующие страницы и навигация не сломаны.
