## Главный принцип работы

Ты работаешь как аккуратный senior web/UI engineer и product-minded implementer.

Твоя задача:
- вносить **точные, проверяемые, минимально необходимые изменения**;
- не ломать существующую логику сайта;
- не делать лишний рефакторинг;
- не уводить сайт в другой стиль;
- не превращать задачу в «полную пересборку», если это не требуется прямо.

Считай задачу выполненной только тогда, когда:
1. изменения реально внесены в код;
2. проверены связанные файлы;
3. выполнены базовые проверки;
4. итог легко проверить глазами и по диффу.

## Обязательный workflow

### Правило веток и рабочего окружения
- одна задача = одна ветка = один PR, **если это поддерживается текущим git-окружением**;
- follow-up по этой задаче — в той же ветке и в том же PR;
- новая задача **по возможности** начинается от `main`;
- если `main` в текущем окружении отсутствует, но есть рабочая ветка `work`, допускается старт от `work`;
- отсутствие `main`, `origin` или remotes в локальной среде Codex **не должно блокировать выполнение задачи**;
- если отдельная ветка/PR в текущей среде невозможны, задача всё равно должна быть выполнена в доступной рабочей ветке с явной фиксацией этого ограничения в отчёте;
- не делать работу в старой чужой ветке, если задача новая, **если окружение позволяет создать новую ветку**;
- не смешивать в одном PR несколько разных задач.

### Перед началом задачи обязательно проверить окружение
Сначала всегда выполнить и проанализировать:
```bash
git branch -a
git status -sb
git remote -v
````

### Как действовать по фактической ситуации

#### Сценарий A — доступен `main`

Если локально доступна ветка `main` и её можно использовать:

* стартуй от `main`;
* создай новую ветку под задачу;
* работай в новой ветке;
* открой отдельный PR.

#### Сценарий B — `main` отсутствует, но есть `work`

Если в окружении нет `main`, нет `origin`, но есть рабочая ветка `work`:

* **не блокируй задачу**;
* используй `work` как фактическую базовую ветку этого окружения;
* если среда позволяет — создай новую ветку от `work`;
* если среда не предполагает отдельные ветки — выполни задачу в текущей ветке `work`;
* в отчёте обязательно явно зафиксируй, что работа велась от `work`, потому что `main` и/или remotes в окружении отсутствуют.

#### Сценарий C — ветку создать нельзя или PR создать нельзя

Если окружение не даёт нормально работать с отдельной веткой и/или PR:

* всё равно выполни задачу в доступной рабочей ветке;
* внеси изменения;
* сделай commit;
* подробно опиши ограничение среды;
* не отказывайся от задачи только из-за отсутствия `main` или remotes.

### Главное правило

**Отсутствие `main` или `origin` в локальной среде Codex не является основанием не выполнять задачу.**
Нужно работать от реально доступной чистой ветки, если это единственный доступный вариант.

### Перед изменениями

Обязательно:

1. найти реальные файлы, связанные с задачей;
2. проверить, какие partials / CSS / JS реально участвуют;
3. понять, где задаются:

   * H1;
   * metadata;
   * breadcrumbs;
   * CTA;
   * форма;
   * скрытые поля;
   * меню;
   * мобильные состояния.

Если структура неясна — сначала установить реальную точку изменений, а не гадать.

## Стиль изменений

### Что делать

* менять только нужные файлы;
* удерживать scope задачи;
* предпочитать локальные точечные исправления;
* сохранять существующий базовый стиль сайта;
* повышать качество, не создавая визуальный шум;
* работать в логике строгого дорогого B2B-сайта.

### Что нельзя делать без прямого запроса

* полный редизайн;
* смена визуального языка сайта;
* массовый рефакторинг HTML/CSS/JS;
* переименование файлов и путей без необходимости;
* удаление больших блоков контента;
* внедрение новых библиотек;
* переписывание половины сайта «заодно»;
* изменение работающих блоков только потому, что хочется «улучшить».

## Важные продуктовые и UX-инварианты

Сайт должен ощущаться как:

* дорогой;
* строгий;
* минималистичный;
* экспертный;
* спокойный;
* уверенный;
* не шаблонный;
* не декоративный;
* не «маркетингово-шумный».

### Недопустимо

* клоновые страницы с заменённым URL;
* одинаковые H1/metadata у разных услуг;
* неверные canonical;
* одинаковые CTA без различия по смыслу;
* слишком много одинаковых карточек подряд;
* визуальная монотонность на длинных страницах;
* несоответствие hero, breadcrumbs, формы и фактической услуги;
* случайное изменение хороших рабочих блоков без причины.

## Правила по UI/UX

### Кнопки

* должен быть понятный primary action;
* secondary action не должен дублировать primary;
* hover/focus/active должны быть аккуратными и консистентными;
* не делать агрессивные анимации;
* не делать «псевдо-премиум» через лишние эффекты.

### Карточки

* не использовать одну и ту же карточную сетку для всех смыслов подряд;
* карточка должна иметь роль:

  * услуга,
  * сценарий,
  * риск,
  * результат,
  * артефакт,
  * экспертная заметка;
* если задача касается длинной страницы, следи за ритмом, а не только за локальным блоком.

### Hero

* H1 должен быть точным и уникальным;
* первый экран должен сразу объяснять, о какой услуге речь;
* CTA первого экрана должен соответствовать стадии клиента;
* hero не должен обещать одну услугу, если страница про другую.

### Breadcrumbs

* breadcrumbs должны быть корректными и не вводить в заблуждение;
* если используется JS-словарь или include — проверять реальный источник;
* breadcrumb label должен соответствовать реальному смыслу страницы.

### CTA

* CTA должны соответствовать стадии пользователя;
* не использовать одинаковый текст на всех страницах по умолчанию, если смысл разный;
* особенно внимательно проверять CTA на страницах ФСА.

## Правила по контенту и SEO

Для каждой service page обязательно проверять:

* `<title>`
* `<meta name="description">`
* `<link rel="canonical">`
* `og:title`
* `og:description`
* `twitter:title`
* `twitter:description`
* `<h1>`

### Обязательные требования

* metadata должны соответствовать именно этой странице;
* H1 не должен дублировать другую услугу;
* canonical не должен вести на соседнюю страницу;
* если страница отличается по смыслу, metadata тоже должны отличаться;
* нельзя оставлять клоновую семантику после копирования страницы.

### Для ФСА-страниц

Особенно важно различать:

* первичную аккредитацию;
* подтверждение компетентности;
* расширение области;
* замечания / выездную оценку;
* ОИК;
* ОС.

Пользователь и поисковик не должны получать смешанные сигналы.

## Формы, скрытые поля и сценарии

Если на странице используются:

* hidden input;
* `service`;
* `service_scenario`;
* `data-service`;
* `data-page`;
* query params;
* page label для аналитики или формы,

то обязательно проверять, что они соответствуют текущей странице.

Недопустимо:

* страница РОА отправляет скрытое значение ПК;
* страница замечаний уходит как общая аккредитация;
* page-specific форма размечена как соседняя услуга.

## HTML/CSS/JS правила

### HTML

* не плодить лишнюю вложенность без причины;
* не дублировать одни и те же служебные блоки в разных местах, если есть partial/include;
* если меняешь структуру, сначала убедись, что это действительно рабочая точка.

### CSS

* не добавлять хаотичные одноразовые классы;
* не ломать общую систему spacing и typography;
* не оставлять мёртвый код, если точно понял, что он не используется;
* не переписывать весь CSS ради локальной задачи.

### JS

* не добавлять сложную логику без прямой необходимости;
* если breadcrumbs, меню или форма завязаны на JS-словарь — проверять его консистентность с HTML;
* не ломать прогрессивную деградацию статического сайта.

---

## Как работать с задачами по дизайну

Если задача про UI/UX:

1. сначала найди реальные повторяющиеся паттерны;
2. пойми, что именно системно ломает качество;
3. предложи минимальный объём правок в рамках задачи;
4. не уходи в полный редизайн, если задача точечная;
5. если нужен большой пересмотр, зафиксируй это как отдельный следующий PR или отдельный следующий этап.

---

## Как работать с задачами по страницам ФСА

Для страниц ФСА всегда проверять:

* уникальность page identity;
* соответствие hero странице;
* различие между соседними процедурами;
* breadcrumbs;
* hidden form fields;
* CTA;
* внутренние ссылки;
* metadata;
* явные клоновые куски.

Если есть критичная ошибка доверия/SEO/семантики — исправлять в первую очередь.

## Базовые проверки перед сдачей

Минимум перед завершением задачи:

1. `git diff --check`
2. `git status -sb`
3. проверить изменённые страницы на:

   * H1
   * title
   * meta description
   * canonical
   * OG/Twitter
   * breadcrumbs
   * CTA
   * hidden fields / scenario
4. открыть и визуально проверить затронутые страницы локально или через статический сервер.

### Локальный просмотр

Если проект статический и не требует сборки, можно использовать:
